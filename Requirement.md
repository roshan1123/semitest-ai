# SemiTest AI – MVP Prototype Requirements

**Document:** Requirement.md  
**Product:** SemiTest AI – Semiconductor Test Intelligence Platform  
**Version:** 1.0  
**Status:** Initial Development Specification  
**Development approach:** Phased development using GitHub Copilot in Visual Studio Code  
**Initial operating mode:** Simulation only – no physical hardware  
**Target prototype:** Working web-based semiconductor testing and analytics application

---

# 1. Project Overview

## 1.1 Product Vision

SemiTest AI is a software platform designed to support semiconductor component testing, test-data management, inspection, traceability and analytics.

The initial MVP will simulate semiconductor testing workflows for discrete semiconductor components, particularly:

- MOSFET
- Diode

The platform will simulate test instruments and semiconductor electrical characteristics without requiring physical testing equipment.

The objective is to demonstrate how semiconductor test data can be generated, processed, evaluated, stored, analysed and reported through a unified software platform.

## 1.2 Business Objectives

The MVP should demonstrate the following business capabilities:

1. Semiconductor device registration and management.
2. Simulated electrical testing of semiconductor components.
3. Configurable test parameters and acceptance limits.
4. Automated PASS / FAIL / REVIEW evaluation.
5. Test history and device traceability.
6. Test-data visualisation and analytics.
7. AI-assisted visual inspection using sample images.
8. Downloadable test reports.
9. Extensible architecture for future physical instrument integration.

## 1.3 MVP Success Criteria

The MVP will be considered successful when a user can:

1. Open the application dashboard.
2. Register a semiconductor component.
3. Select a MOSFET or diode test profile.
4. Execute a simulated test.
5. View generated electrical measurements.
6. Evaluate the results against configured limits.
7. Save the results in a database.
8. View historical test results.
9. Analyse test trends.
10. Generate and download a PDF or CSV report.

All test results must clearly indicate that they are simulated.

## 2.2 Explicitly Excluded from MVP

The following capabilities are outside the initial scope:

- Physical semiconductor testing.
- Direct connection to real instruments.
- Actual semiconductor wafer testing.
- Production-grade ATE control.
- High-voltage or high-current testing.
- Destructive semiconductor testing.
- Semiconductor fabrication process control.
- Automated machine learning model training.
- Production MES integration.
- Customer enterprise authentication integration.
- Real-time factory equipment monitoring.
- Certified or accredited measurement functionality.

These features may be considered in future releases.

## 2.3 Simulation-Only Requirement

The application must operate entirely without hardware.

Implement a mandatory operating mode:

`SIMULATION_ONLY`

Requirements:

- The application must start without connected instruments.
- All test measurements must be generated by software.
- Every simulated measurement must be marked as simulated.
- The UI must display a visible SIMULATION MODE indicator.
- No real hardware communication should be attempted.
- Hardware execution must be disabled by default.
- No API endpoint should initiate a physical measurement.
- Test reports must explicitly state that measurements are simulated.

# 4.3 Test Profile Management

Test profiles define which measurements are simulated and how results are evaluated.

A test profile must be associated with a device category.

### Profile attributes

- Profile ID.
- Profile name.
- Device category.
- Profile version.
- Test description.
- Measurement definitions.
- Acceptance limits.
- Unit of measurement.
- Enabled / disabled status.
- Created by.
- Created timestamp.

### MOSFET test profile

The MVP must support these illustrative measurements:

| Measurement | Description | Unit |
|---|---|---|
| VGS threshold | Simulated gate-source threshold voltage | V |
| RDS(on) estimate | Simulated on-state resistance estimate | mΩ |
| IDSS | Simulated drain-source leakage under defined conditions | µA |

Each measurement must support:

- Lower acceptance limit, where applicable.
- Upper acceptance limit, where applicable.
- Unit.
- Measurement configuration.
- Evaluation method.

### Diode test profile

| Measurement | Description | Unit |
|---|---|---|
| Forward voltage | Simulated forward voltage drop | V |
| Reverse leakage | Simulated reverse leakage current | µA |

### Important engineering rule

Do not hardcode generic semiconductor acceptance limits and present them as industry-standard limits.

For the prototype:

- Provide clearly labelled illustrative default profiles.
- Allow administrators to change limits.
- Require limits to be configured for the relevant device and test conditions.
- Store the profile version used for every test execution.
- Store the conditions under which each measurement was generated.

# 4.4 Test Execution Engine

This is the core MVP functionality.

The user must be able to execute simulated MOSFET and diode tests.

### Test execution workflow

1. Select semiconductor device.
2. Select test profile.
3. Display test parameters and acceptance limits.
4. Confirm test execution.
5. Generate simulated measurement data.
6. Evaluate measurement results.
7. Display individual measurement status.
8. Calculate overall test status.
9. Save results to the database.
10. Display the completed test report.

### Test record attributes

- Test ID.
- Device ID.
- Device part number.
- Device category.
- Test profile ID.
- Test profile version.
- Execution timestamp.
- Operator.
- Simulation indicator.
- Simulator version.
- Measurement results.
- Overall test status.
- Test duration.
- Test notes.

### Result evaluation logic

For each measurement:

- PASS: Measurement falls within the configured acceptance range.
- FAIL: Measurement falls outside the configured acceptance range.
- REVIEW: Measurement cannot be evaluated reliably, required limits are missing, or the result is invalid.

Overall result:

- FAIL if at least one valid measurement fails.
- REVIEW if no measurement fails but one or more measurements require review.
- PASS only if every required measurement passes.

The system must never automatically classify a measurement with missing acceptance limits as PASS.

# 4.5 Simulated Instrument Engine

Create a dedicated simulation service.

Suggested interface:

`SimulatedInstrument`

The simulator must generate synthetic measurements for different semiconductor device categories.

### Simulation requirements

- Generate repeatable results using an optional random seed.
- Support configurable normal distributions or other documented distributions.
- Support nominal values and variation.
- Support random noise.
- Support normal, borderline and abnormal test scenarios.
- Support forced PASS, FAIL and REVIEW scenarios.
- Generate measurement timestamps.
- Generate test execution metadata.
- Identify all generated readings as simulated.

### Example simulation scenarios

**Scenario A – Normal device**

Measurements are generated around the configured nominal values and normally fall within the acceptance limits.

**Scenario B – Borderline device**

Measurements are generated close to an acceptance boundary. Some tests may pass while others require review or fail.

**Scenario C – Abnormal device**

At least one measurement is intentionally generated outside its configured limit.

**Scenario D – Invalid measurement**

Generate an invalid or missing measurement to test the REVIEW evaluation workflow.

### Simulator configuration

Provide configuration for:

- Scenario selection.
- Random seed.
- Noise level.
- Variation percentage.
- Number of measurements.
- Optional delay to simulate instrument execution time.

The simulator must be deterministic when the same configuration and random seed are used.

- Keep business logic separate from API routes.

- Use database migrations.
- Maintain consistent error handling.
- Use environment-based configuration.
- Design the instrument interface for future extension, without implementing hardware connectivity now.

# 9. API Requirements

Use REST APIs under:

`/api/v1`

## 9.1 System

| Method | Endpoint | Purpose |
|---|---|---|
| GET | /health | Application health |
| GET | /system/mode | Confirm simulation-only mode |

## 9.2 Devices

| Method | Endpoint | Purpose |
|---|---|---|
| POST | /devices | Register device |
| GET | /devices | List devices |
| GET | /devices/{id} | Device details |
| PUT | /devices/{id} | Update device |
| GET | /devices/{id}/tests | Device test history |

## 9.3 Test Profiles

| Method | Endpoint | Purpose |
|---|---|---|
| POST | /profiles | Create profile |
| GET | /profiles | List profiles |
| GET | /profiles/{id} | Profile details |
| PUT | /profiles/{id} | Update profile |

## 9.4 Test Execution

| Method | Endpoint | Purpose |
|---|---|---|
| POST | /tests/execute | Execute simulated test |
| GET | /tests | List test executions |
| GET | /tests/{id} | Test details |
| GET | /tests/{id}/measurements | Test measurements |

Example request:

```json
{
  "device_id": "DEVICE-001",
  "profile_id": "MOSFET-DEFAULT",
  "scenario": "NORMAL",
  "random_seed": 12345
}
```

Example response:

```json
{
  "test_id": "TEST-00001",
  "device_type": "MOSFET",
  "simulation_mode": true,
  "scenario": "NORMAL",
  "overall_status": "PASS",
  "measurements": [
    {
      "parameter": "VGS_THRESHOLD",
      "value": 2.45,
      "unit": "V",
      "status": "PASS"
    },
    {
      "parameter": "RDS_ON",
      "value": 42.5,
      "unit": "mOhm",
      "status": "PASS"
    }
  ]
}
```

The numerical values above are illustrative synthetic values only. They must not be presented as real device measurements or universal semiconductor limits.

- Report download interactions.
- Image upload validation.

## 12.3 Critical Business Logic Test Cases

| Test Case | Expected Result |
|---|---|
| All measurements within limits | PASS |
| One measurement outside limits | FAIL |
| One invalid measurement and no failures | REVIEW |
| One failure and one invalid measurement | FAIL |
| Missing required measurement | REVIEW |
| Missing configured limits | REVIEW |
| Same simulator seed and configuration | Same synthetic readings |
| Different simulator seeds | Potentially different readings |
| Hardware execution requested | Rejected |

## 12.4 Simulation Data Quality

The simulator should generate plausible and explainable data.

It must:

- Use documented synthetic distributions.
- Use explicit measurement units.
- Use realistic value precision for the simulation.
- Support edge cases.
- Keep raw generated values.
- Avoid presenting synthetic distributions as empirical semiconductor manufacturing data.

# 13. Non-Functional Requirements

## 13.1 Performance

- Dashboard should normally load within 3 seconds with a small demonstration dataset.
- Device listing should support pagination.
- Test result retrieval should be efficient.
- Image uploads should have configurable size limits.
- Long-running operations should provide clear progress or status.

## 13.2 Reliability

- Database transactions must be used for test persistence.
- Failed executions must not leave partially committed test records.
- Application errors must be logged.
- Application should recover after restart.
- Database backups should be documented.

## 13.3 Security

- Validate all API inputs.
- Do not expose secrets in frontend code.
- Use environment variables for configuration.
- Restrict uploaded file types.
- Use generated filenames for uploads.
- Prevent path traversal.
- Keep audit records for important administrative operations.
- Avoid storing unnecessary personal data.

## 13.4 Maintainability

- Use modular architecture.
- Use type hints.
- Use clear naming conventions.
- Document complex business logic.
- Avoid duplicate business logic.
- Use database migrations.
- Write automated tests.
- Maintain a clean README.

## 13.5 Extensibility

The system must be designed so that future releases can add:

- Real SCPI instruments.
- USB and serial instruments.
- Additional semiconductor components.
- Wafer-level test data.
- More advanced AI inspection.
- Manufacturing execution system integration.
- Production deployment.
- Multi-tenant enterprise support.

These are architectural extension points only; physical hardware integration is not part of the MVP implementation.
